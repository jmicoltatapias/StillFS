# S3-compatible API v1 (limited subset)

StillFS accepts path-style requests at the HTTP root. This is a deliberately
limited subset, not a claim of general S3 compatibility. Health checks remain
unauthenticated. The status UI is served under `/console/`; `/` belongs to the
S3 service listing.

## Operations

| Method and path | Behavior |
| --- | --- |
| `GET /` | XML `ListAllMyBucketsResult`, limited to buckets owned by the signing principal |
| `PUT /{bucket}` | Create an empty bucket for the signing principal |
| `HEAD /{bucket}` | Check an owned bucket; foreign and missing buckets both appear absent |
| `DELETE /{bucket}` | Delete an empty owned bucket |
| `PUT /{bucket}/{key}` | Create or replace one object, streaming its request body |
| `GET /{bucket}/{key}` | Stream bytes and return stored object headers |
| `HEAD /{bucket}/{key}` | Return metadata after checking that referenced bytes can be opened |
| `DELETE /{bucket}/{key}` | Remove metadata and then safely attempt byte cleanup; deleting a missing key is idempotent |
| `GET /{bucket}?list-type=2` | List objects with `prefix`, `delimiter`, `max-keys`, `start-after`, and continuation tokens |

Bucket names use a documented subset of S3 DNS-style names: 3–63 lowercase
letters, digits, dots, or hyphens, no adjacent dots, no `.-`/`-.`, and no
IPv4-form address. Object keys must be nonempty valid UTF-8, at most 1024 bytes,
and contain XML 1.0-safe characters. Keys are never filesystem paths.

ListObjectsV2 accepts `max-keys` from 1 through 1000 (default 1000). It returns
keyset-paginated `Contents` and delimiter-derived `CommonPrefixes`. Continuation
tokens are opaque base64url cursors scoped to prefix and delimiter, but are not
cryptographically sealed. Pages do not share a database snapshot. Query
parameters other than the documented subset are rejected. `encoding-type=url`,
legacy list operations, bucket location/configuration, object subresources,
range requests, tags, ACLs, user metadata, and multipart operations are not
implemented.

For AWS SDK for Go v2, the API accepts an exact `x-id` query marker matching
the implemented operation (for example `x-id=GetObject`). It is signed as part
of the canonical query and cannot select or expose any other operation.

Only `Content-Type` and `x-amz-checksum-sha256` are accepted as object metadata.
The checksum header is base64 SHA-256 and must agree with the signed payload
digest. User `x-amz-meta-*`, `Content-MD5`, and other object metadata headers
are rejected rather than silently discarded. Content type and listing metadata
are bounded by `STILLFS_MAX_METADATA_BYTES`; all request headers are bounded by
`STILLFS_MAX_HEADER_BYTES`; object bodies are bounded by
`STILLFS_MAX_OBJECT_BYTES` (default 5 GiB).

## SigV4 mode

Only `Authorization: AWS4-HMAC-SHA256 ...` header authentication is accepted.
The credential scope must be `YYYYMMDD/{STILLFS_S3_REGION}/s3/aws4_request`.
The default region is `us-east-1`; `x-amz-date` is required and checked against
`STILLFS_S3_CLOCK_SKEW` (default five minutes). `host` and `x-amz-date` must be
signed; content type, content MD5, and other signed `x-amz-*` headers are also
required to appear in `SignedHeaders`.

Every request must carry a lowercase hexadecimal `x-amz-content-sha256` for
one payload. Non-PUT operations must use the empty-payload SHA-256. PUT object
streams bytes to the local backend while recomputing SHA-256; metadata is not
committed if the actual body digest differs. The signature is compared in
constant time. Canonicalization preserves path separators and repeated slashes,
URI-encodes bytes with uppercase escapes, and encodes/sorts query components
after decoding them.

Unsupported modes are rejected: `UNSIGNED-PAYLOAD`, SigV4 streaming/chunk
signatures and trailers, presigned URLs, SigV2, SigV4a, session/security tokens,
other AWS services, and other regions. This is narrower than the modes Amazon
S3 supports; see the [AWS S3 SigV4 reference](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html).

## Credential setup

The server stores credential secrets encrypted with AES-256-GCM and access-key
ID as associated data. Configure `STILLFS_CREDENTIAL_ENCRYPTION_KEY` with the
legacy base64-encoded 32-byte key, or set
`STILLFS_CREDENTIAL_ENCRYPTION_KEY_FILE` to a protected raw 32-byte key file.
See [authorization and local administration](authorization-admin.md) for
backup, rotation, recovery, and file-permission requirements.

The local-only `stillfsctl credential create` command creates a principal and
credential and prints the secret once. A new key receives no permissions unless
one or more `--permission ACTION` flags are supplied. Supported actions are
`s3:ListBuckets`, `s3:ListObjects`, `s3:CreateBucket`, `s3:DeleteBucket`,
`s3:GetObject`, `s3:PutObject`, and `s3:DeleteObject`. A key attached with
`--principal-id ID` still receives only its own assigned actions. Use
`stillfsctl credential permissions set ACCESS_KEY_ID` to replace permissions;
omitting `--permission` removes all permissions. `stillfsctl credential revoke
ACCESS_KEY_ID` revokes a key. Unknown permissions are rejected. There is no
public credential endpoint, default S3 key, AWS IAM policy language,
credential self-service, or administrative permission.

Run `stillfsctl` only from a trusted local operator account that can reach the
configured PostgreSQL database and read the credential-encryption key. Protect
that account, the database role, the key file (mode `0600`), and command output;
the generated secret is printed to stdout once and should be captured only in a
protected terminal/session. The CLI is an administrative bootstrap mechanism,
not a remotely authenticated credential service. Revoke a lost or exposed key
with `stillfsctl credential revoke ACCESS_KEY_ID`.

Example creating a key with the full current S3 data-plane subset:

```sh
stillfsctl credential create \
  --permission s3:ListBuckets --permission s3:ListObjects \
  --permission s3:CreateBucket --permission s3:DeleteBucket \
  --permission s3:GetObject --permission s3:PutObject --permission s3:DeleteObject
```

This is a fixed StillFS permission list, not AWS IAM. Permissions are checked
after SigV4 authentication and before looking up bucket or object data;
ownership checks still apply after permissions.

Migration `0002_identity_ownership.sql` adds nullable bucket ownership without
assigning legacy buckets to a new principal. Unowned legacy buckets are
invisible to S3 and return `NoSuchBucket`; assign ownership explicitly through
an audited database operation before exposing them.

## Responses and consistency

Successful object PUT/GET/HEAD responses include an ETag of the form
`"sha256-<hex>"`. It is an opaque StillFS ETag, not MD5. The independent
`x-amz-checksum-sha256` is base64 encoded. Errors use S3-style XML and codes;
HEAD error responses have no body, as required by HTTP semantics.

Create and replacement write bytes before metadata. Replacements and deletes
are serialized by a per-key lock inside the single process. Delete removes the
metadata row before checking for remaining references and attempting to delete
bytes. This relies on StillFS's existing single-process local-root contract;
it does not make PostgreSQL and the filesystem atomic. Failures can leave
orphaned bytes, and process crashes can leave stale references. There is no
reconciler. Put the service behind TLS; the HTTP server does not terminate TLS.

### Executed client compatibility test

The repository's reproducible compatibility test uses AWS SDK for Go v2
`service/s3` v1.113.2 with Go 1.27.3, HTTP path-style addressing, and an
ephemeral credential stored in an isolated PostgreSQL test schema. It has been
executed against PostgreSQL and the local filesystem backend. The test covers
bucket create/head/list/delete, duplicate-bucket errors, object PUT/GET/HEAD/
DELETE, empty and 3.5 MiB streaming bodies, ListObjectsV2 prefix/delimiter
pagination, missing-key and non-empty-bucket errors, response metadata, SigV4,
and revocation. It does not validate AWS CLI or other SDK versions.

Run it against a disposable PostgreSQL database with:

```sh
STILLFS_TEST_DATABASE_URL='postgres://user:password@127.0.0.1:5432/stillfs_test?sslmode=disable' \
  make test-s3-compat
```

The test generates its own access key and secret and revokes the key before
finishing. The AWS SDK v2 dependency is isolated under `tests/s3compat`, so it
does not raise the Go version required to build the StillFS server. The SDK is
Apache-2.0 licensed; see the [upstream SDK license](https://github.com/aws/aws-sdk-go-v2/blob/main/LICENSE.txt).
